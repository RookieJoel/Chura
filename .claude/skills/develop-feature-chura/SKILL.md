# Chura Feature Development Loop

Act as senior engineer for `Chura`, a student Agile project-management tool
(Team Member / Auditor roles, Project → Backlog → Sprint → Ticket domain —
see `CONTEXT.md` at repo root for full glossary). Follow the pipeline below.

## Hexagonal architecture notes (backend)

Every backend story crosses these layers, outside-in for design, inside-out
for implementation:

- `internal/domain` — entities (Project, Ticket, Sprint, ...), no framework/DB imports.
- `internal/port/in` — use-case interfaces adapters call (driving ports).
- `internal/port/out` — repository/gateway interfaces services depend on (driven ports).
- `internal/service` — use-case implementations; the only place business logic lives.
- `internal/adapter/http` — Fiber handlers; translate HTTP ⇄ port/in calls, no logic.
- `internal/adapter/postgres` — implements port/out via sqlc-generated queries (`sqlcgen`, regenerated by `make -C backend generate`, never hand-edited).

A new capability typically adds: a domain type (if new), a port/in interface,
a port/out interface (if new persistence need), a service implementing
port/in against port/out, an http handler wired to the service, and (if
schema changes) a goose migration + sqlc query + regenerated `sqlcgen`.

## Pipeline

```
P0 Init  →  P1 Grill   →  P2 Spec  →  P3 Design  →  P4 Tickets →  P5 Implement →  P6 Review  →  P7 PR
   gate      +domain       gate        gate          gate           loop + TDD     2-axis       gate
             model                                                                 + reviewer
   ─────────────── deep-reasoning model ──────────────────────┤├──────────── standard model ──────────
```

Follow phases in order. Do not write implementation code before the user
approves P3. P1–P4 (thinking) should run on your most capable model; P5–P7
(execution) can run on a cheaper/faster model via delegated agents.

### Gate economy

Five human gates (P0, P2, P3, P4, P7) suits a feature touching schema, API
and UI. For a small feature (single surface, no migration, no new
permission check) collapse P2+P3 into **one** combined approval and say so
when you present it. Never collapse P0 or P7. Never collapse a gate on a
feature touching anything in `security_sensitive_domains`.

## Phase 0: Spine & Init

- Read `progress.md` — determine if resuming or fresh. If resuming, jump to the phase the entry names.
- Read `CONTEXT.md` for domain vocabulary. Use its terms in every artifact. If a term is missing or fuzzy, that's a P1 grilling question, not something to invent.
- Confirm branch/worktree state with `git status` in whichever of `backend/`, `frontend/` the feature touches.
- Pick the feature slug. Check `features/<feature-slug>/` — if it exists, this is a resume.

### Spec is an output, not a precondition

A hand-written `spec.md` is **not** required to start. Accept any of:

- A rough idea or one-liner from the user → P1 grills it into shape, P2 writes `spec.md`.
- An existing `features/<slug>/spec.md` or excerpt from `proposal.md` → still run P1 to grill its gaps, then P2 rewrites it into the template, preserving every requirement it already states.

Never **invent requirements**. A generated `spec.md` may only contain what
the user said in the P1 interview, what the codebase shows, or what
`proposal.md`/`service.md` establish. Anything else is a P1 question you
failed to ask.

### Kickoff plan gate (before any branch/file creation)

Before creating the branch or touching any files, present a short kickoff
plan and wait for explicit approval:

- Feature slug + one-line scope summary
- Which of `backend/`, `frontend/` are touched and the branch name to create
- Which phases this run will go through, noting skippable ones and whether you propose collapsing P2+P3 per *Gate economy*
- Anything already known that's likely to need a grilling question or a design decision — surface it here

On approval: create branch `claude/feature-<feature-slug>` off `main`. Never
work directly on `main`. Add an `## In Progress` entry for
`<feature-slug>` in `progress.md` before starting P1, so state survives a
dropped session.

## Phase 1: Grill with docs (deep-reasoning model)

A relentless design interview that produces domain docs as it goes.

Run together, they interleave, not sequential:
- `Skill(skill: "mattpocock-skills:grilling")` — drives the interview
- `Skill(skill: "mattpocock-skills:domain-modeling")` — captures vocabulary and decisions as they crystallise

### Split questions by who can answer them

- **Facts are your job, never the user's.** Framework behavior, library API, what the existing code already does → dispatch to a sub-agent (docs lookup, codebase search). Don't block the round on it.
- **Decisions are the user's.** Permission scope (Team Member vs Auditor), error-surfacing behavior, single- vs multi-select, partial-failure behavior — these are the actual grilling questions.

### Domain modeling, inline

- **Challenge against the glossary.** If the user's term conflicts with `CONTEXT.md`, say so immediately and make them pick.
- **Sharpen fuzzy language.** Pin down which specific entity (Project/Ticket/Sprint/Template/...) a vague noun refers to.
- **Cross-reference with code.** If the user states how something works and the code disagrees, surface the contradiction.
- **Update `CONTEXT.md` inline** the moment a term resolves — glossary only, no implementation details, one-or-two-sentence definitions with rejected-synonym notes. Never batch to the end.

### Where decisions get recorded

Backend-scoped architectural decisions (framework, persistence, structural
conventions) go in `backend/docs/adr/NNNN-title.md` (template and index in
`backend/docs/adr/README.md`). Feature-scoped decisions that don't rise to
an ADR go in a `Decisions` section appended to the feature's `spec.md`
(Further Notes). Offer a decision record only when all three hold — hard
to reverse, surprising without context, the result of a real trade-off. If
any is missing, skip it; a small clarification is a grilling-log line, not
a decision record.

**Do not proceed until the user confirms shared understanding.** The
frontier being empty is your signal to ask; their confirmation is the gate.

## Phase 2: Synthesise the spec (deep-reasoning model, gate)

**No interview here** — P1 already did it. Synthesise into
`features/<feature-slug>/spec.md`.

Delegate the write to a Write-capable agent on your deep-reasoning model.

### Seams first

Sketch the **seams** at which this feature gets tested before writing the
spec. Prefer existing seams; fewer is better, one is ideal.

- Backend: the `internal/adapter/http` handler (highest, via an in-process Fiber test app), the `internal/service` (port/in) interface, the `internal/adapter/postgres` (port/out) implementation.
- Frontend: the rendered component via a testing-library-style render (highest), a custom hook in `src/hooks/`, a function in `frontend/src/api/`.

**Check the proposed seams with the user before writing the spec.**

### Spec template

Write `features/<feature-slug>/spec.md` with these sections, using
`CONTEXT.md` vocabulary throughout:

- **Problem Statement** — from the user's perspective, naming the actual role (Team Member / Auditor).
- **Solution** — the solution from the user's perspective.
- **User Stories** — numbered list, `As a <Team Member|Auditor>, I want <feature>, so that <benefit>`.
- **Implementation Decisions** — modules built/modified, port/service interfaces changed, schema changes, API contracts, specific interactions. No file paths, no code snippets, except a snippet that encodes a decision precisely (state machine, schema, type shape).
- **Testing Decisions** — the agreed seams, which modules get tested, prior art in the repo for that test type.
- **Out of Scope** — explicitly.
- **Further Notes** (including any Decisions recorded per P1).

Present `spec.md` and **wait for approval**.

## Phase 3: Technical design (deep-reasoning model, gate)

Produce `features/<feature-slug>/design.technical.md`, covering whatever
applies:

- **DB schema**: new/changed tables, columns, constraints, indexes. Migration file name(s) under `backend/db/migrations/` (goose format: `<timestamp>_<slug>.sql`).
- **sqlc queries**: new/changed `.sql` files under `backend/db/queries/`, and that `make -C backend generate` regenerates `backend/internal/adapter/postgres/sqlcgen` (never hand-edited).
- **API docs**: update `backend/docs/api/openapi.yaml` with the new/changed paths, request/response schemas, and required role — this is the design output for the API contract, not a separate follow-up task.
- **Hexagonal wiring**: which `port/in` and `port/out` interfaces are added/changed, which `domain` types are added/changed, which `service` implements the use case.
- **API contract**: Fiber routes, handler signatures, request/response shapes, status codes, error cases, which role (Team Member/Auditor) can access it.
- **Frontend**: component tree, route(s) under `frontend/src/app/`, state ownership (local vs shared), new functions in `frontend/src/api/`, route-guard changes if new protected paths.
- **Test seams**: restate the P2-agreed seams concretely — which package/file, which existing test is prior art.
- **Risks/dependencies**: migration ordering, cross-project access control, any external touchpoints.

Present and **wait for explicit approval before writing tickets or touching
code.** If a question surfaces here that P1 should have caught, go back and
grill it — don't guess.

## Phase 4: Tickets (deep-reasoning model, gate)

Tracker is local markdown under `features/<feature-slug>/issues/`.

### Draft vertical slices

Break the work into **tracer bullets**:

- Each slice cuts a narrow but COMPLETE path through every hexagonal layer it touches — migration → sqlc query → domain/port → service → http adapter → frontend api client → component → test. **Vertical, never a horizontal slice of one layer.**
- A completed slice is demoable or verifiable on its own.
- Each slice fits in a single fresh context window.
- Prefactoring first: "make the change easy, then make the easy change."

Give each ticket its **blocking edges**.

**Wide refactors are the exception** — sequence expand–contract instead
(see general pattern: expand ticket adds new form beside old, migrate
tickets move call sites in blast-radius-sized batches, contract ticket
deletes the old form).

### Quiz the user

Present the breakdown as a numbered list — **Title**, **Blocked by**,
**What it delivers**. Ask about granularity and blocking-edge correctness.
Iterate until approved.

### Publish

On approval write one file per ticket under `features/<feature-slug>/issues/`:

```markdown
# <NN>: <Ticket title>

**What to build:** the end-to-end behaviour this ticket makes work, from
the user's (Team Member/Auditor) perspective.

**Blocked by:** the numbers/titles gating this one, or "None (can start immediately)".

**Status:** ready-for-agent

- [ ] Acceptance criterion 1
- [ ] Acceptance criterion 2
```

This is the last deep-reasoning-model output for the feature. Everything
after is execution against these tickets.

## Phase 5: Implement (standard model, loop)

Work stories in dependency order, top-to-bottom through the ticket list
(`uses_ralph_loop: false` — no automated loop driver; you drive it).

Implementation per story runs via a delegated executor agent on your
standard model. Reserve the deep-reasoning model for the case where a
reviewer FAIL reveals the **design** was wrong (not just the
implementation) — kick that specific gap back to P3 before resuming.

### TDD, at the agreed seams

Call `Skill(skill: "mattpocock-skills:tdd")` for the loop's rules. Bites
hardest here:

- **Test only at the seams agreed in P2/P3.** No test at an unconfirmed seam.
- **Red before green.** One seam, one test, one minimal implementation per cycle.
- **No horizontal slicing** — never all tests then all implementation.
- **No tautological assertions** — expected values come from a known-good literal, a worked example, or the spec, never recomputed the way the code computes them.
- **Refactoring is not part of the red→green loop**; it belongs to review.

### Backend stories (hexagonal)

1. Migration file(s) first under `backend/db/migrations/` (apply locally via `make -C backend migrate-up`). Add/update `.sql` files in `backend/db/queries/`, run `make -C backend generate`.
2. **RED**: table-driven tests at the agreed seam — happy path, invalid input, role rejection (Team Member vs Auditor), edge cases (nil/empty, errors). Run `make -C backend test`, confirm the new test fails for the right reason.
3. **GREEN**: minimal `domain` type → `port/out` interface → `adapter/postgres` implementation → `port/in` interface → `service` implementation → `adapter/http` handler → route registration.
4. **REFACTOR**: wrap/annotate errors per Go convention, keep interfaces small, `make -C backend lint`, `make -C backend test` with coverage, 80%+ on new code.

### Frontend stories

1. For meaningful UI surface, sketch a throwaway mock first to validate layout/interaction before building the real tree.
2. Build per Next.js App Router convention (`frontend/src/app/`), PascalCase components under `frontend/src/components/`, `use`-prefixed hooks under `frontend/src/hooks/`. Local state unless genuinely cross-cutting.
3. Wire against mock data first to isolate UI bugs, then connect the real endpoint via `frontend/src/api/`.
4. Verify: `pnpm --dir frontend typecheck`, `pnpm --dir frontend lint`, `pnpm --dir frontend test`.
5. **Manually exercise the golden path and error states in a running dev server (`pnpm --dir frontend dev`) before claiming done.** Typecheck and tests verify correctness, not that the feature works in a browser. Name what the harness bypassed.

### State ownership

- The ticket files own the **human-readable** unit of work; tick their checkboxes as stories pass.
- `progress.md` stays **feature-level**: one line in `## In Progress` until every story passes and P7 is done, then it moves to `## Done`.

Run typechecks and single test files continuously; run the full suite once
at the end. Commit to the feature branch as tickets complete.

### Terminal conditions

- All stories pass, verification passes, P7 PR opened → move the `progress.md` entry to `## Done`, report the PR link.
- The same reviewer FAIL reason recurs 3x on one story → stop, add an `## Open / Needs a Human` entry naming the story. Do not retry blindly.

## Phase 6: Two-axis review + maker-checker gate

Never mark your own diff as reviewed.

### 6a. Two-axis review

Call `Skill(skill: "mattpocock-skills:code-review")` with the fixed point
being the branch point (`git merge-base` against `main` in whichever of
`backend/`, `frontend/` changed).

Report both verbatim under `## Standards` and `## Spec`. **Do not merge or
rerank the two.**

### 6b. Mandatory reviewer gate

No `local_reviewer_agent` configured — skip. If one is added later, wire
it here per the generic template.

### 6c. Language and security reviewers

In parallel with 6a, not instead of: `go-reviewer` for `backend/` changes,
`typescript-reviewer` for `frontend/` changes, and `security-reviewer` if
the feature touches anything in `security_sensitive_domains` (auth,
Team Member/Auditor role checks, cross-project access).

### Rules for all checks

- Every reviewer runs the checks themselves — build, lint, typecheck, test suite. **A claim of "tests pass" from you is not evidence.**
- **FAIL** from any reviewer → fix in branch, re-run the specific failed checks, resubmit. Same FAIL reason 3 times → stop and escalate to `## Open / Needs a Human` in `progress.md`.
- **PASS** from every invoked reviewer → P7.

## Phase 7: Human gate & PR

- Do not merge into `main` directly.
- Push `claude/feature-<feature-slug>` with `-u`. Confirm with the user before pushing if not already authorized this session.
- Open the PR via `gh pr create` against `RookieJoel/Chura` with:
  - Summary of what changed and why, linking `spec.md`
  - Test plan: `make -C backend test` / `pnpm --dir frontend test` as applicable, coverage, manual verification notes / screenshots for UI changes
  - Reviewer verdicts: the two-axis review's per-axis summary, and which language/security reviewers ran
- Commit messages: `<type>: <description>` (`feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `ci`), plus whatever attribution trailer this session's instructions require.
- Update `progress.md`: move the entry from `## In Progress` to `## Done` with a one-line summary and the PR link.

## Strict Rules

1. No vibe coding — "it compiles" is not done. Tests green + lint + typecheck clean, all required.
2. Never invent a requirement. If it wasn't in the interview, the codebase, or `proposal.md`/`service.md`, it's a question, not a spec line.
3. Never hand-edit `backend/internal/adapter/postgres/sqlcgen` — always regenerate via `make -C backend generate`.
4. Never hardcode secrets/API keys/credentials — env vars only (`DATABASE_URL`, etc.).
5. Changes touching `security_sensitive_domains` are security-sensitive — mandatory security-reviewer pass, no exceptions, no collapsed gates.
6. `CONTEXT.md` is a glossary and nothing else — no specs, no scratch notes, no implementation decisions.
7. Context hygiene — delegate heavy subtasks (large test-suite generation, multi-file exploration) to subagents rather than loading it all into main context.
8. Any destructive git op (`reset --hard`, force-push, branch delete) requires explicit user confirmation first.
