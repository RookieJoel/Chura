**ADR-007: Load Testing Tool**

| Title | Load Testing Tool |
| :---- | :---- |
| **Context** | Chura needs a repeatable way to measure how the backend behaves under concurrent use, starting with the Sprint and Work Item flow: a Team Member creates a Sprint, creates a Work Item, assigns it to the Sprint, then reads the Sprint and its metrics. That flow crosses two transports. Sprints are REST endpoints on the Go API, while Work Items are created and updated over the `/ws/work-items` WebSocket, and the Sprint metrics read depends on the internal gRPC call from the Sprint service to the Work Item service. Every request also needs a Keycloak bearer token, and since ADR-006's amendment every Project and Sprint request triggers a Keycloak Admin API membership lookup, so Keycloak is part of what is under load. The test has to script a multi-step, stateful flow (ids from one response feed the next request), authenticate per virtual user, cover both HTTP and WebSocket in one scenario, report latency per endpoint and per WebSocket operation, and fail clearly when a latency or error budget is exceeded. It should run from the command line against the local `make dev` stack, live in the repository next to the code, and be written in a language the team already uses.<br><br>The alternatives considered are Apache JMeter, Locust, Gatling, Artillery, and single-endpoint tools such as `hey`, `vegeta`, and `ghz`. JMeter can script the flow, but test plans are XML edited through a GUI, which makes review in pull requests hard, and WebSocket support needs a third-party plugin. Locust is scripted in Python, which no part of Chura uses, and WebSocket clients have to be written by hand on top of its user classes. Gatling has first-class WebSocket support, but its scripts are written in Scala, Java, or Kotlin, and it needs a JVM in the toolchain. Artillery is JavaScript-based and supports WebSockets, but it runs on Node.js and its per-request thresholds and metric tagging are less direct than k6's. `hey` and `vegeta` only hammer a single HTTP endpoint and cannot express a stateful flow or WebSockets, and `ghz` only targets gRPC directly, which would bypass the REST and WebSocket edges users actually hit. k6 is a single Go binary, is scripted in JavaScript, has built-in `k6/http` and `k6/ws` modules, supports `setup()` and `teardown()` for shared fixtures, and has tags, custom metrics, and thresholds that turn a run into a pass or fail result. |
| **Decision** | Use k6 for backend load testing. Keep scripts in `loadtest/` at the repository root, one script per user flow, starting with `loadtest/sprint-workitem.js`. Drive the system only through its public edges (REST and WebSocket), not by calling gRPC services directly. Each virtual user logs in through the Keycloak password grant and logs in again shortly before its token expires. Use `setup()` to create the shared fixtures (a Project and its members) and `teardown()` to remove the data the run created. Tag every request by endpoint and record WebSocket round trips in a custom `ws_op_duration` trend tagged by operation, and set thresholds on error rate, check rate, and p95 latency per tag so that a run exits non-zero when a budget is missed. Run it through `make loadtest` for the full ramping profile and `make loadtest-smoke` (1 VU, 1 iteration) to check that the flow still works after an API change. |
| **Status** | **Accepted** |
| **Consequences** | **Positive**<br>• One script covers the REST, WebSocket, and Keycloak parts of the flow, so the results reflect what a real Team Member's session costs, including the gRPC call and Keycloak membership lookups behind it.<br>• Scripts are plain JavaScript files that are reviewed in pull requests like any other code, in a language the team already uses for the frontend.<br>• Thresholds give a clear pass or fail result (`http_req_failed` below 1%, checks above 99%, p95 below 500 ms per endpoint and WebSocket operation), so a regression shows up as a failed run instead of a number someone has to interpret.<br>• Per-endpoint tags and the `ws_op_duration` trend show which step is slow, rather than one blended latency figure.<br>• k6 is a single binary with no runtime to manage, and the smoke target is cheap enough to run after any change to the endpoints the flow uses.<br>**Negative**<br>• k6 is not part of `make check-tools`, so each developer has to install it separately.<br>• k6 runs JavaScript in its own embedded runtime, not Node.js, so npm packages and Node APIs are not available to scripts; helpers have to be written for k6 or imported as k6-compatible modules.<br>• The scripts depend on details that can drift from the code: the WebSocket message shapes (`create`, `update`, `list`, `delete` and their replies), the seed users and password in the local Keycloak realm, and Direct Access Grants (password grant) being enabled on `chura-auth-client`. An API change that does not update the script breaks the load test, which the smoke target is meant to catch.<br>• Results are only meaningful for the local dev stack, where k6, the backend, Postgres, RabbitMQ, and Keycloak compete for the same machine; they are useful for comparing changes, not for predicting production capacity.<br>• Teardown cannot delete the Project or its Keycloak group because there is no delete endpoint yet (#22), so each run leaves one `k6-loadtest-*` Project to remove by hand.<br>• Load tests are not run in CI yet; they are run manually. |
