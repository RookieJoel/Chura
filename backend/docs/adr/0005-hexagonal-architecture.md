**ADR-005: Backend Architecture Pattern**

| Title | Backend Architecture Pattern |
| :---- | :---- |
| **Context** | Chura's backend implements multiple business services (Project Configuration, Agile Execution, Analytics & Reporting) with cross-service collaborators and server-side authorization, inside a Go modular monolith. The team wants business logic decoupled from the HTTP framework and the database so either can change independently, and use cases stay testable without a live database. Hexagonal architecture is also a good fit for Go's interface-based design, and this project is being built for the Software Architecture course, so the team chose it deliberately to get hands-on familiarity with the pattern. |
| **Decision** | Structure `backend/internal` as hexagonal ports and adapters: `domain` (entities, no framework deps), `port/in` (use-case interfaces), `port/out` (repository/gateway interfaces), `service` (use-case implementations — the only place business logic lives), `adapter/http` (driving adapter), `adapter/postgres` (driven adapter). |
| **Status** | **Accepted** |
| **Consequences** | **Positive**<br>• Business logic testable via `port/in` against in-memory `port/out` fakes, no DB required.<br>• The HTTP framework and the database are both swappable behind their adapter boundary.<br>• Matches the Modular Monolith direction with clear package boundaries.<br>• Fits Go's interface-oriented style and gives the team practical experience with the pattern for the course.<br>**Negative**<br>• More files/indirection per feature than a typical MVC layout.<br>• The team must learn the new concept like ports, adapters, and the dependency-direction discipline it requires. |
