**ADR-009: Identity Provider**

| Title | Identity Provider |
| :---- | :---- |
| **Context** | Chura needs one authentication system for Team Members and Auditors across the Next.js frontend and Go backend. It must support OpenID Connect, issue signed tokens that the backend can validate through JWKS, and provide groups and roles for authorization. Chura also needs to represent project groups so that access can be controlled within a project. Authentication should stay outside the application, while the backend must still enforce authorization independently of the frontend. The alternatives considered are Supabase, Firebase Authentication, Google SSO, application-managed authentication, and Keycloak.<br><br>Supabase provides authentication together with database features, but Chura would depend on Supabase-specific services that it does not need for identity management. Firebase Authentication is easy to start with, but it focuses on authentication and would require additional application infrastructure for Chura's groups, roles, and project-group permissions. Google SSO provides a familiar sign-in experience, but it mainly addresses authentication through Google accounts and does not provide Chura's application-specific RBAC and project-group model. Application-managed authentication gives the team full control, but makes the team responsible for password storage, token issuance, account recovery, security maintenance, and the complete groups and permissions model. External identity providers can handle user authentication, but Chura would still need additional infrastructure and synchronization logic to manage RBAC, user groups, and project groups. Keycloak provides users, groups, roles, and standard OpenID Connect tokens in one system, which fits Chura's authorization requirements while keeping authentication outside Chura's business services. |
| **Decision** | Use Keycloak as Chura's identity provider and authorization foundation. Configure the `chura` realm with OpenID Connect clients, users, groups, and realm roles. Integrate the Next.js frontend through Auth.js, and validate bearer access tokens in the Go backend through Keycloak's JWKS endpoint. Use Keycloak groups and roles as inputs to the backend's Team Member, Auditor, and project-group authorization decisions. |
| **Status** | **Accepted** |
| **Consequences** | **Positive**<br>• Keeps authentication and account management outside Chura's business services.<br>• Provides standard OpenID Connect flows for the Next.js frontend and signed JWTs for backend verification.<br>• Provides users, groups, and roles that support Team Member, Auditor, and project-group authorization.<br>• Lets the backend validate tokens independently through the Keycloak JWKS endpoint.<br>• Avoids building separate infrastructure to synchronize external identities with Chura's RBAC and project-group model.<br>• Runs locally through Docker Compose, which supports consistent development and testing.<br>**Negative**<br>• The team must run and maintain Keycloak, its database, realm configuration, and client settings.<br>• Developers must understand OpenID Connect, token lifetimes, JWKS rotation, groups, roles, and redirect URI configuration.<br>• Realm configuration changes may require a realm re-import or an update to an existing Keycloak instance because imported settings are not automatically reapplied to an existing data volume. |


**Amendment (2026-10-09): Project membership and Project Role live in Keycloak**

| Title | Project membership and Project Role live in Keycloak |
| :---- | :---- |
| **Context** | The first Project Configuration iteration stored Project members and Project Roles in a Postgres `project_members` table keyed by a user id sent in request headers. Authentication has since moved to Keycloak JWTs (a user's identity is the token `sub`), so membership is now a second copy of identity data that can drift from the identity provider and does not follow a user's removal or deactivation. This ADR already commits to Keycloak as the single place for users, groups and roles. Alternatives considered: keeping the Postgres membership table (a second source of truth, with a synchronisation problem for every identity change), and carrying Project groups in a token `groups` claim (a removal would only take effect when the token expires, so access would outlive membership). |
| **Decision** | Model each Project as a Keycloak group named `project-<projectId>` and store each member's Project Role as the single-valued user attribute `chura_project_role_<projectId>`, writable by administrators only (user profile `unmanagedAttributePolicy: ADMIN_EDIT`). Postgres keeps only the Project row, including `keycloak_group_id`. The backend authenticates to the Keycloak Admin API as the `chura-backend` service account (client credentials; roles `view-users`, `manage-users`, `query-groups` only) and reads membership on every request that needs it, so a removal takes effect on the next request. Keycloak has no cross-system transaction, so creation is an ordered write (group, creator membership and role, then the Postgres row) with a reverse undo on failure; undo failures are logged with the project and group ids. A Keycloak failure that is not a definite answer surfaces as `503 service unavailable`. |
| **Status** | **Accepted** (amends the decision above) |
| **Consequences** | **Positive**<br>• One source of truth for identity and membership; removing a user from the group revokes access on the next request.<br>• No identity data duplicated in Postgres and no token-staleness window.<br>• The Project row carries no user data beyond the creator's id.<br>**Negative**<br>• Keycloak is now on the request path of every Project and Sprint call; when it is down those calls return 503.<br>• Every such request makes at least one Admin API call (plus an occasional service-account token refresh).<br>• There is no cross-system transaction, so a failed undo can leave an orphan Keycloak group (logged, no reconciler).<br>• The Admin API replaces a user's whole attribute map on update, so role writes are read-modify-write and two concurrent writes for the same user in different Projects can overwrite each other.<br>• The local realm must be re-imported (data volume recreated) to pick up the new client, user profile policy and seed users. |
